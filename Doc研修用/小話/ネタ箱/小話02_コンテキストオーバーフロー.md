## スライド1

### メインメッセージ
> **「急にAIが馬鹿になった」には、物理的な理由がある**

### 見せるもの

**あるある：長く使っていると、こうなる**
- さっき渡したはずの設計書の内容を、平然と無視しはじめる
- 「〇〇のルールで」と言ったのに、序盤と違う書き方をしはじめる
- 途中で作業が止まる／勝手に省略する

**原因：入れ物には、物理的な上限がある**
```
 ┌───────── コンテキストウィンドウ（上限） ─────────┐
 │ ①システムプロンプト │②ルール│③設計書│④会話ログ… │
 └──────────────────────────────────────────────────┘
                                              会話が伸びる ▶

 ┌───────── コンテキストウィンドウ（上限） ─────────┐
 │②ルール│③設計書│④会話ログ ███████████████████████│
 └──────────────────────────────────────────────────┘
   ▲ 溢れると、古いほうから押し出される／要約されて潰れる
     ＝ 序盤に渡した「一番大事な前提」から先に失われる
```

**入るのに、効かなくなることもある**

| 現象 | 何が起きているか |
|---|---|
| 🚪 **押し出し** | 上限を超え、古いやり取りが落ちる・要約に置き換わる |
| 🌫 **薄まる** | 入ってはいるが、大量の情報の中で埋もれ、重みが下がる |
| 🐢 **重くなる** | 毎ターン全部読み直すので、長いほど遅く・高くなる |

### 話すこと
- 「AIが急に馬鹿になった」は、感覚ではなく**構造上そうなります**。入れ物のサイズが決まっているからです
- そして厄介なのが、**溢れると古い方から消える**ということ。序盤に渡した設計書やルール、つまり一番大事な前提が最初に失われます
- しかもAIは「忘れました」と言ってくれません。**忘れたことに気づかないまま、それらしく続きを書きます**（→ 小話05）

## スライド2

### メインメッセージ
> **闘い方は3つ。「切る」「置く」「渡し直す」**

### 見せるもの

**🛡 対策1｜切る ── 長い1本より、短い複数本**
```
 ❌ 1セッションで CD → UT → 機能追加 を全部やる
      └ 終盤には序盤の前提が残っていない

 ✅ 機能単位・工程単位で区切る
      CD で1本 ／ UT で1本 ／ 機能追加で1本
      └ 各セッションが「必要な情報だけ」で満たされる
```

**🛡 対策2｜置く ── 記憶はファイルに持たせる**

| 会話に溜める（❌） | ファイルに置く（✅） |
|---|---|
| 「さっき言った命名規則で」 | `モジュール一覧.md` を読ませる |
| 「前に直したあの書き方で」 | `CD_ルール.md` に書いておく |
| 「仕様はこう決めたよね」 | 外部設計書を更新しておく |

> 会話は**揮発する**。ファイルは**次のセッションでも効く**

**🛡 対策3｜渡し直す ── 大事な前提は、要所で再提示する**
- 長いやり取りの後で重要な作業に入るときは、**設計書のパスをもう一度書く**
- 「①どこを見るか」を毎回添えるだけで、押し出しの影響をかなり潰せる（→ 小話13）

**🚨 溢れかけのサイン**
- 序盤に指示したルールと違う書き方が出てきた
- 「（要約しました）」「コンテキストを圧縮しています」の表示が出た
- 同じ質問を繰り返してくる／既に読んだファイルをまた読み直している

**👀 そして今は「勘」ではなく、数字で見えます**

主要なAIツールには、**今どれだけ入れ物を使っているかを表示する機能**が用意されています。

| ツール | 見かた |
|---|---|
| **GitHub Copilot（VS Code）** | チャット入力欄の**右上のリング型アイコン**。クリックすると使用率（％）と、会話・ファイルなど**何がどれだけ占めているかの内訳**が出る |
| Claude Code | `/context` コマンドで内訳を表示。自動圧縮までの残量も出る |
| その他のCLI系ツール | 画面下部に「context left ○％」のような残量表示があるものが多い |

> ⚠ 上限そのものは**モデルの性能ではなくツール側が決めている**ことに注意。同じモデルでも、使うツールによって入る量は違います

**使い方は簡単で、「重い作業に入る前に一度見る」だけ**
- 8割を超えていたら、新しいセッションを開いてから始める
- 「何が場所を食っているか」が分かるので、**無駄に読ませたファイル**にも気づける
- Copilotなら「Summarize conversation」／`/compact` で手動圧縮もできる（ただし細部は落ちる → 補足参照）

### Take away
- ✅ **上限は物理制約**。気合や言い方では回避できない
- ✅ **セッションは消耗品**。長く使うほど品質が落ちる。こまめに切るのが正しい使い方
- ✅ **設計書＝AIの外部記憶**。今日のspec駆動は、この制約への対策そのもの（→ 小話10）
- ✅ **残量は見える**。勘に頼らず、重い作業の前にインジケーターを一度確認する
- ⚠ ループが長引くほど経緯が膨らむ（→ 小話03）。**大きな依頼を1発で投げないこと**が最大の予防策

### 話すこと
- 対策はシンプルです。**溜めない・置く・渡し直す**。この3つだけ覚えて帰ってください
- そして今は、**残量を数字で見られます**。Copilotならチャット入力欄の右上に小さなリングがあるので、その場で一度クリックしてみてください。「今何％使っているか」「何が場所を食っているか」が出ます
- 「なんとなく調子が悪い」を待つのではなく、**重い作業の前に一度見る**。これだけで切るタイミングを外さなくなります
- 特に効くのが「切る」です。もったいない気がして1本を引っぱりがちですが、**新しく開いた方が速くて安くて正確**なことがほとんどです
- そして今日の研修の構成そのものが、この対策になっています。工程ごとに分けて、設計書という外部記憶を持たせて、必要なところだけ読ませている。**これは丁寧にやっているのではなく、そうしないと動かないからです**

## 補足（質問が出たら）
- **Q. 上限を増やせばいい？** → 増えてはいるが、入れるほど「薄まる」「遅い」「高い」が効いてくる。入れないのが最善
- **Q. 圧縮（compact）されたらどうなる？** → 要約に置き換わるので、細部（正確なパス・数値・命名）は落ちやすい。圧縮後は前提を渡し直すのが安全
- **Q. インジケーターが出ていない／見当たらない** → VS Code・拡張機能のバージョンで表示が変わることがある。まずアップデートを確認する。無い場合も、対策1〜3（切る・置く・渡し直す）は変わらず有効
- **Q. 最初から数十％使っているのはなぜ？** → システムプロンプトやツール定義、応答用に確保された枠が最初から入っているため。**ゼロから始まるわけではない**のが普通
