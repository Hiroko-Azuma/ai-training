# 小話14　ルールファイルは"組織の暗黙知"の置き場所

|項目|内容|
|---|---|
|分類|🛠 実務|
|尺|5分（スライド2枚）|
|推奨タイミング|`CD_ルール.md` の説明をした直後|

---

## スライド1

### メインメッセージ
> **毎回「Lombokを使って」と言い続けますか？**

### 見せるもの

**掴み：AIに毎回言っていること、ありませんか**
```
 「Lombok使ってください」
 「例外はこの形で握ってください」
 「コメントはこの書式で」
 「ログはここで出してください」
 「メソッド名はこの規則で」
```
→ しかも**セッションを切ると全部リセット**される（→ 小話01）

**その"毎回言っていること"は、たいてい組織の暗黙知**

| どこに存在しているか | 誰が知っているか |
|---|---|
| レビューでの口頭指摘 | ベテランの頭の中 |
| 「うちはこう書く」という慣習 | 古参メンバーだけ |
| 過去の障害から生まれたルール | 経緯を知る人だけ |
| コーディング規約（読まれていない） | 一応ドキュメントにはある |

**ルールファイルは、その置き場所**
```
 CD_ルール.md
   ├─ アーキテクチャの決まりごと
   ├─ 命名規則
   ├─ 実装スタイル
   └─ サンプルコード      ◄── これが一番効く
```

### 話すこと
- ルールファイルというと「AI用の設定ファイル」に聞こえますが、中身は違います。**これまで人の頭とレビューの中にあった知識**です
- 新人にやってもらう時と同じですよね。「うちのやり方はこれです」と最初に渡すか、毎回レビューで指摘するか
- AIは新人と違って**指摘を覚えません**。だから書いておくしかない。逆に言えば、**書いておけば100%守ります**

## スライド2

### メインメッセージ
> **レビューで毎回言っていることは、一度書けば二度と言わなくてよい**

### 見せるもの

**運用サイクル ── レビュー指摘を資産に変える**
```
 ① AIの出力をレビューする
        ↓
 ② 指摘する（例：「ここはLombokの@Slf4jで」）
        ↓
 ③ ★ その場でルールファイルに1行足す ★   ◄── ここが肝
        ↓
 ④ 以降、その指摘は二度と発生しない
        ↓
 ⑤ 次のPJにも、そのルールファイルを持っていける
```

**書き方のコツ**

| ❌ 効きにくい | ✅ 効く |
|---|---|
| 「読みやすく書くこと」 | **「1メソッドは50行以内」** |
| 「適切に例外処理すること」 | **サンプルコードを1つ載せる** |
| 「規約に従うこと」 | 具体的な命名例を並べる |
| 長文の理念・背景説明 | **やること／やらないことの箇条書き** |

> 💡 一番効くのは**サンプルコード**。「これに倣って」の一言で、命名も構造も作法もまとめて伝わる（→ 小話08）

**効果が出る場所**

| 効果 | 中身 |
|---|---|
| 🎯 品質の均一化 | 誰が指示しても同じ作法で出てくる（→ 小話06 のゆらぎ対策） |
| ⏱ レビュー時間の削減 | 形式的な指摘が消え、**仕様の妥当性に集中できる**（→ 小話15） |
| 📚 教育資産 | 新人にもそのまま渡せるドキュメントになる |
| 🔁 横展開 | PJの規約が、そのまま次のPJの資産になる |

### Take away
- ✅ **毎回言っていることは、ルールファイルに書く**。それだけで指摘がゼロになる
- ✅ 抽象的な理念ではなく、**具体例とサンプルコード**を書く
- ✅ レビューの指摘は、その場で**ルールに還元する**。これをやるかどうかで半年後が変わる
- 💰 ルール整備は**先行投資**。見積りにも明示的に積む（→ 小話18）

### 話すこと
- 今日使っている `CD_ルール.md` を、ぜひ「AIの設定ファイル」ではなく「**PJの規約が実際に効いている状態**」として見てください
- これまでコーディング規約って、書いても読まれませんでしたよね。AIは**必ず読んで、必ず守ります**。規約が初めてちゃんと機能する、とも言えます
- 自PJに持ち帰る時の最初の一歩は、**レビューで直近3回言ったことを書き出す**ことです。それだけでルールファイルの原型ができます
