# 小話13　悪いのはAIか、指示か ── 切り分けの手順

|項目|内容|
|---|---|
|分類|🛠 実務|
|尺|6分（スライド2枚）|
|推奨タイミング|UT待ち／うまくいかない受講者が出てきた頃|

---

## スライド1

### メインメッセージ
> **「AI、使えないですね」の前に確認する4つ**

### 見せるもの

|# | 疑う原因 | 症状（こう見える） | 打ち手 |
|---|---|---|---|
| ① | **情報不足** | 存在しないクラスを使う／既存と違う書き方をする | 設計書・既存コード・ルールをコンテキストに入れる |
| ② | **あいまい** | 意図と違うものが出る／毎回ブレる | 完了条件を書く（「〜が通ること」） |
| ③ | **一度に多すぎ** | 途中で息切れ／後半が雑／勝手に省略する | 画面単位・機能単位に分割する |
| ④ | **そもそも無理** | 何度やっても堂々巡り | 前提を人間が決めてから渡す |

```
 出力がおかしい
      │
      ├─ 前提知識を渡したか？ ──── No ──► ①情報を足す
      │      Yes
      ├─ 完了条件は書いたか？ ──── No ──► ②条件を書く
      │      Yes
      ├─ 依頼が大きすぎないか？ ── Yes ──► ③分割する
      │      No
      └─ 人間なら書けるか？ ────── No ──► ④まず人間が決める
```

### 話すこと
- うまくいかない時、原因はだいたいAI側ではなく**渡し方**にあります。しかもパターンは多くない
- これは障害調査と同じで、**切り分けの型**を持っているかどうかで解決速度が変わります
- 「①〜④のどれか」と口に出して考えるだけで、闇雲な言い直しがなくなります

---

## スライド2

### メインメッセージ
> **プロンプトはコード。書き直せば、ちゃんと直る**

### 見せるもの

**❌ Before**
```
ログイン機能を作って
```
→ AIは、テーブル構造も画面仕様も既存の作法も知らない。**全部推測で埋める**

**✅ After**
```
Docsシステム/外部設計/05個別画面設計/BK01.md の仕様どおりに
ログイン画面と Controller を作成してください。

・クラス名は モジュール一覧.md に従うこと
・実装スタイルは CD_ルール.md のサンプルコードに倣うこと
・完了条件：mvn compile が通ること
```
→ ①情報 ②完了条件 ③範囲 が全部入っている

**書き直しの4パーツ**

| パーツ | 中身 | 効果 |
|---|---|---|
| 📍 **どこを見るか** | 設計書のパス、参考にする既存クラス | 推測を止める |
| 🎯 **何を作るか** | 対象を1つに絞る | 息切れを防ぐ |
| 📏 **どう作るか** | ルールファイル、サンプル | 書き方のブレを止める |
| ✅ **完了条件** | ビルドが通る／テストが緑 | AIが自分で検証できる |

### Take away
- ✅ **闇雲に言い直さない**。①〜④のどれかを特定してから直す
- ✅ 特に効くのは **「完了条件」**。これがあるとAIは自分で確かめてから返してくる
- ⚠ **3往復して直らないなら、直すのをやめる**。会話に誤りが溜まって余計こじれます。プロンプトを直して**新しいセッションでやり直す**方が速い（→ 小話11）

### 話すこと
- 一番よくあるのは①の情報不足です。人間の新人なら「これどのテーブル使うんですか」と聞き返してくれますが、AIは聞き返さずに埋めてしまう
- 逆に言うと、**新人に頼む時に説明することを、そのまま書けばいい**。特別なテクニックは要りません
- そして意外と効くのが完了条件です。「mvn compile が通ること」と書くだけで、AIが自分でビルドして直してから返してくるようになります
