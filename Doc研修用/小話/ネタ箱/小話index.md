# AI小話一覧

AI活用に際しての小話を入れたい。

## 使い方の前提
- ハンズオン中、AIの実行待ち（5〜10分）に挟むショートセッション
- 1本 = **スライド2枚相当 / 話す時間 3〜7分**
  - 1枚目：掴み（問い・あるある）＋ 図解1つ
  - 2枚目：仕組みの答え ＋ 実務への持ち帰り（Take away）
- 受講者像：SE。ChatGPTでチャットしたことはあるが本格活用はこれから
- したがって **「用語の定義」より「なぜそうなるか」→「だからどう使うか」** の順で組み立てる

## 分類
| 記号 | 分類 | ねらい |
|---|---|---|
| 🔧 | 仕組み | ブラックボックス感を減らす。挙動が予測できるようになる |
| 🛠 | 実務 | 明日から手が変わる。作業の型を持ち帰ってもらう |
| ⚠ | リスク・マインド | やってはいけない事／期待値の調整 |

## 各小話メモ

### 01. なぜAIはステートレスなのに会話が続くのか（セッションの正体）🔧 ※既存ネタ
- **掴み**：「さっきの続きで」と言うと通じる。AIは覚えている…のか？
- **核**：毎回、過去の全会話を丸ごと送り直しているだけ。APIは1回1回が完全に独立
- **持ち帰り**：会話が長いほど毎ターン重くなる。話題が変わったら新しいチャットへ

### 02. Contextサイズオーバーフローとの闘い 🔧 ※既存ネタ
- **掴み**：長く話していたら急にAIが馬鹿になった、忘れた、途中で止まった
- **核**：コンテキストウィンドウという物理的な上限。溢れると圧縮・切り捨てが起きる
- **持ち帰り**：長い1本より短い複数本。設計書を「読ませる場所」として使い、会話に記憶を溜めない

### 03. いま画面の向こうで何をしているのか（エージェントループ）🔧
- **掴み**：この5分、AIはずっと考え込んでいるのか？（＝いま目の前で起きている待ち時間そのものを題材にする）
- **核**：「考える → ツールを使う（ファイルを読む/書く/mvnを叩く）→ 結果を見てまた考える」のループ。1回の指示の裏で数十回のAI呼び出しが走っている
- **持ち帰り**：待ち時間はAIが手を動かしている時間。ログを眺めると何で詰まったかが分かる／ツールを与えるほど自走する
- **図**：Think→Act→Observe の円環図（研修画面のログと対応づけると刺さる）

### 04. トークンという単位 ―「日本語は高い」の理由 🔧
- **掴み**：課金も上限も「文字数」ではない
- **核**：単語より細かい断片＝トークン。英語は1単語≒1トークン、日本語は1文字で1〜2トークン食うことも
- **持ち帰り**：桁感（このハンズオンの1回の生成で何万トークン）を体感値として持つ。設計書の冗長さはコストに直結

### 05. なぜAIは平然と嘘をつくのか（次単語予測とハルシネーション）🔧
- **掴み**：存在しないメソッドを、堂々とサンプル付きで教えてくる
- **核**：AIは「正しさ」ではなく「それらしさ」を最大化している。知らないと言うより、もっともらしく続ける方が自然
- **持ち帰り**：だから**検証可能な形**で使う（コンパイル・テスト・設計書との突合）。この研修のUTフェーズがまさにその装置

### 06. 同じ指示なのに毎回結果が違う 🔧
- **掴み**：隣の人と同じプロンプトなのに出力が違う
- **核**：確率分布からのサンプリング。同じ問いに毎回同じ答えを返す仕組みになっていない
- **持ち帰り**：「再現しない」を前提に運用設計する。品質はプロンプトではなくルール＋テストで担保する

### 07. AIは文字を数えられない 🔧（箸休め・3分）
- **掴み**：「strawberryにrは何個？」に間違える。掛け算も間違える
- **核**：文字ではなくトークンで世界を見ているから。計算も"それらしい数字"を生成しているだけ
- **持ち帰り**：数える・計算する・正確に集計する系はツール（コード実行）にやらせる。これがAgentの存在意義

### 08. モデルの選び分けと知識カットオフ 🔧
- **掴み**：モデル名がいっぱいあるが、どれを選べばいいのか
- **核**：賢さ・速さ・コストのトレードオフ。加えて学習データには締切日があり、最新ライブラリは知らない
- **持ち帰り**：設計・難所は上位モデル、定型変換は軽量モデル。最新情報は自分でContextに与える

### 09. 全部読ませる vs 探して渡す（RAG）🔧
- **掴み**：システム全部を読ませれば完璧なのでは？
- **核**：物理的に入らないし、入っても薄まる。必要な部分だけ検索して渡すのがRAG。エージェントのファイル探索も同じ発想
- **持ち帰り**：「探しやすい構造」の設計書・コードほどAIの精度が上がる。命名とディレクトリ構成がAI可読性

### 10. なぜ「設計書を渡す」と精度が跳ね上がるのか（spec駆動の理由）🛠
- **掴み**：「いい感じの書籍管理画面作って」と言った時と、設計書を渡した時の差
- **核**：AIの出力品質は入力コンテキストの質でほぼ決まる。設計書＝AIに渡す仕様のシングルソース
- **持ち帰り**：**コードが正 → 設計が正** への転換。設計書を直せばコードが追従する世界（今日の機能追加フェーズで体験する）
- ※研修全体の背骨。できれば早い時間に

### 11. 直すより作り直す ― やり直しの経済学 🛠
- **掴み**：おかしくなった会話を必死に修正して、余計こじれた経験
- **核**：誤った出力もコンテキストに残り、後の出力を汚染する。修正の継ぎ足しは負債の複利
- **持ち帰り**：3往復直らなければ捨てる。プロンプトを直して**新規セッションでやり直す**方が速くて安い

### 12. Gitはシートベルト ― AI時代のコミット粒度 🛠
- **掴み**：AIが50ファイル書き換えた。戻せますか？
- **核**：AIは大胆に広範囲を変える。差分レビューと巻き戻しが唯一の安全装置
- **持ち帰り**：AIに投げる前にコミット。動いたらコミット。「捨てられる状態」を常に保つ

### 13. 悪いのはAIか、指示か ― 切り分けの手順 🛠
- **掴み**：「AI使えないですね」と言う前に確認したい4点
- **核**：①情報を渡していない（コンテキスト不足）②あいまい（受け取り方が複数ある）③一度に多すぎ ④そもそも人間でも無理な依頼
- **持ち帰り**：デバッグと同じ。切り分けの型を持つ。ダメなプロンプトと直したプロンプトの実例を並べて見せる

### 14. ルールファイルは"組織の暗黙知"の置き場所 🛠
- **掴み**：毎回「Lombok使って」「コメントはこの形式で」と言うのか？
- **核**：CD_ルール.md のようなルール／サンプルコードが、レビュー指摘を先回りして潰している
- **持ち帰り**：レビューで毎回言っていることは、ルールファイルに書けば二度と言わなくてよい。PJの規約がそのまま資産になる

### 15. レビュー観点はどう変わるか 🛠
- **掴み**：AIが書いたコード、どこを見る？
- **核**：構文ミス・タイポは激減し、**仕様の取り違え・過剰実装・境界条件**が主戦場になる。動くコードほど危ない
- **持ち帰り**：「書ける人」より「読んで判断できる人」の価値が上がる。設計意図との突合がレビューの中心に

### 16. 入れてはいけない情報 ― 学習利用と企業契約の話 ⚠
- **掴み**：顧客データ、貼ってもいいですか？
- **核**：個人利用のチャットと企業契約／APIでは、入力の扱い（学習利用の有無・保持期間）が違う
- **持ち帰り**：判断基準を1枚で。迷ったらマスクする／社内ルールの参照先を明示
- ※事実関係は自社の契約・社内規程に合わせて要確認

### 17. 生成コードのライセンスと著作権 ⚠
- **掴み**：このコード、誰のもの？納品していい？
- **核**：学習データ由来の類似コード問題、著作物性の考え方、ツール側の補償制度の有無
- **持ち帰り**：長い定型ブロックの丸写しには注意。社内の取り扱い方針を確認する導線を示す

### 18. 見積りはどう変わるか ⚠
- **掴み**：コーディングが1/5になったら、工数も1/5？
- **核**：減るのは「作る時間」。増える／減らないのは仕様を決める・レビューする・繋ぎ込む・直す時間。ボトルネックが上流に移動する
- **持ち帰り**：AI適用の効果は工程ごとに違う。午後のシミュレーション（自PJへの適用計画）への前振りとして最適

### 19. AIが得意な仕事・苦手な仕事 ⚠
- **掴み**：どこから任せる？
- **核**：得意＝定型変換／量が多い／答え合わせができる。苦手＝暗黙の業務知識／曖昧な合意形成／正解が検証できないもの
- **持ち帰り**：自PJのタスクをこの軸でマッピングしてみる

### 20. 若手はどう育つのか ⚠
- **掴み**：写経で覚えた我々の経験は、これからも成立するか
- **核**：書く経験が減る一方で、読む・判断する能力の必要性は上がる。育成の入口が変わる
- **持ち帰り**：レビュー参加とAI出力の検証を早期に経験させる、という育て方の話（議論を誘発するネタとして）
