# 小話10　なぜ「設計書を渡す」と精度が跳ね上がるのか

|項目|内容|
|---|---|
|分類|🛠 実務|
|尺|6分（スライド2枚）|
|推奨タイミング|CD実行の待ち時間（研修の背骨。できるだけ早い時間帯に）|

---

## スライド1

### メインメッセージ
> **AIの出力品質は、ほぼ「何を渡したか」で決まる**

### 見せるもの

**同じAI・同じモデルでも、渡すものでこれだけ変わる**

|  | ❌ 「いい感じの書籍管理画面を作って」 | ✅ 設計書 ＋ モジュール一覧 ＋ CDルール |
|---|---|---|
| AIがやること | 仕様を**創作**する | 仕様を**翻訳**する |
| 項目名 | それっぽい名前を発明 | 設計書どおり |
| クラス名 | 毎回変わる | モジュール一覧に一致 |
| コーディング規約 | AIの好み | サンプルコードに追従 |
| レビュー | 仕様の確認から始まる | 差分の確認で済む |

```
  ❌ 曖昧な指示                     ✅ 仕様を渡す
        ●                                ●
      ／│＼                            ／│＼
    ／  │  ＼   ← 発散              ＼  │ ／   ← 収束
  ／    │    ＼                        ＼│／
 毎回ちがう成果物                   毎回ほぼ同じ成果物
```

### 話すこと
- 「プロンプトが上手い人」の正体は、凝った言い回しを知っていることではありません。**必要な情報を過不足なく渡している**だけです
- 情報が足りないと、AIは黙って埋めます。埋めた部分が、後でレビューを一番苦しめる
- 今日渡している設計書とルールファイルは、その「埋めさせない」ための材料です

## スライド2

### メインメッセージ
> **「コードが正」から「設計が正」へ ── これがspec駆動開発**

### 見せるもの

**従来の開発**
```
 設計書 ──(人が実装)──► コード
   │                      │
   └─ 書いた瞬間から陳腐化   └─ 真実はこちら
      直しても誰も読まない      「コード見ればわかる」
```

**spec駆動開発**
```
 設計書 ══(AIが生成)══► コード ══► ビルド／テスト
   ▲                                    │
   └────── 変更は必ずここから入れる ──────┘

   設計書を直す → 生成し直す → 検証する
```

**何が変わるか**

|  | 従来 | spec駆動 |
|---|---|---|
| 仕様変更の入口 | コード | **設計書** |
| 設計書の鮮度 | 落ちる一方 | 直さないとコードが出ないので**維持される** |
| 設計書を書く動機 | 成果物だから | **実行される仕様だから** |

### Take away
- 💡 **「設計書を書く時間が惜しい」は逆**。AIに渡す前提で書くと、設計書が初めて"実行される仕様"になる
- 💡 設計書のメンテが続かなかった最大の理由は「直しても何も起きないから」。spec駆動では**直さないとコードが変わらない**
- 🎯 午後の「機能追加」フェーズで、**設計書を直す → 生成し直す**の往復を実際に体験します。今日の一番の持ち帰りはここ

### 話すこと
- 我々が長年悩んできた「設計書とコードが乖離する」問題に、初めて構造的な答えが出た、というのがこの話の要点です
- 乖離したのは怠慢だからではなく、設計書を直すインセンティブが仕組みとして無かったからです
- spec駆動では、設計書がコードの生成元になる。だから直す理由ができる。逆に言うと、**AIに読ませられない設計書には価値がなくなっていく**、という話でもあります
