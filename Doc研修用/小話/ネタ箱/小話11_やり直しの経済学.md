# 小話11　直すより作り直す ― やり直しの経済学

|項目|内容|
|---|---|
|分類|🛠 実務|
|尺|4分（スライド2枚）|
|推奨タイミング|詰まっている受講者が出てきた頃|

---

## スライド1

### メインメッセージ
> **こじれた会話は、直すほど悪くなる**

### 見せるもの

**掴み：あるあるの流れ**
```
 「違う、そうじゃなくて」
 「そこは変えなくていいです」
 「さっきの方が良かったので戻して」
 「なぜまた同じミスを…」
        └ 気づけば30往復。最初より悪化している
```

**なぜ悪化するのか**
```
 ┌── セッション（毎回まるごと読み直される）──────────────┐
 │ 指示A                                                │
 │ ❌ 誤った出力A     ← 消えない                        │
 │ 「違います」                                         │
 │ ❌ 誤った出力B     ← 消えない                        │
 │ 「そうじゃなくて」                                    │
 │ ❌ 中途半端な出力C ← 消えない                        │
 └──────────────────────────────────────────────────────┘
        ▲ AIは毎回この全部を読んでから、次を考える（→ 小話01・03）
          ＝ 誤りの痕跡が、以降の出力を汚染し続ける
```

- 人間なら「さっきのは忘れて」で切り替えられる。**AIは、書いてある物を無かったことにはできない**
- 修正の継ぎ足しは、**負債が複利で増える**のと同じ

### 話すこと
- これ、必ず経験します。というより今日、何人かは既にこの状態かもしれません
- 直感的には「粘り強く直す」のが正しく思えます。でも仕組み上、**誤った出力が全部コンテキストに残り続けて、次の判断に影響します**
- しかも会話が伸びるぶん、遅く・高く・不正確になります（→ 小話02）。**粘るほど条件が悪くなる**んです

## スライド2

### メインメッセージ
> **捨てるのは失敗ではない。いちばん安い解決策**

### 見せるもの

**🔁 3往復ルール**
```
 1往復目  修正指示 ─► 直らない
 2往復目  修正指示 ─► 直らない
 3往復目  修正指示 ─► 直らない
        ↓
 ✋ ここで手を止める
        ↓
 ① git で作業前の状態に戻す        （→ 小話12）
 ② 何が足りなかったかを特定する    （→ 小話13の①〜④）
 ③ プロンプト／設計書を直す
 ④ 🆕 新しいセッションで、1発目からやり直す
```

**コストを比べてみる**

| | 直し続ける | 作り直す |
|---|---|---|
| かかる時間 | 往復のたびに増える | **1〜2往復で終わることが多い** |
| コンテキスト | 誤りが溜まり続ける | **まっさら** |
| 出来上がり | 継ぎはぎ・意図不明の残骸 | 一貫した実装 |
| 次回への資産 | 残らない | **直したプロンプト／設計書が残る** |

> 💡 直し続けても**手元にしか残らない**。作り直すと**プロンプトと設計書が改善される**＝次も効く

**捨てられる状態を保つのが前提**
- AIに投げる前にコミット（→ 小話12）
- 戻せないと「もったいないから直す」しかなくなる

### Take away
- ✅ **3往復して直らなければ、直すのをやめる**。粘るほど条件は悪くなる
- ✅ やり直すのは後退ではない。**一番速くて安いルート**
- ✅ やり直す前に必ず「**なぜ直らなかったか**」を1つ特定する。それをしないと同じ所で止まる
- 💡 直した内容がプロンプトや設計書に残れば、**それは次のPJでも効く資産**になる

### 話すこと
- 我々には「作ったものを捨てるのはもったいない」という感覚が染みついています。AIの前では、それが一番高くつきます
- 手で書いたコードなら、捨てるのは自分の時間の損失です。でもAIの出力は**もう一度作らせれば数分で出てきます**。捨てるコストがほぼゼロなんです
- なので、**「戻せる状態を作っておいて、迷わず捨てる」**。この2つをセットで持ち帰ってください
