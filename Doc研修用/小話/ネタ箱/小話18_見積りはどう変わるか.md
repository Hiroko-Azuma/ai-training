# 小話18　見積りはどう変わるか

|項目|内容|
|---|---|
|分類|⚠ リスク・マインド|
|尺|6分（スライド2枚）|
|推奨タイミング|午後・シミュレーション（自PJへの適用計画）の直前|

---

## スライド1

### メインメッセージ
> **コーディングが5倍速くなっても、プロジェクトは5倍速くならない**

### 見せるもの

**工程ごとに「効き方」がまったく違う**

```
             従来の工数感                AI適用後
 要件定義   ████████                 ████████      → ほぼ変わらない
 設計       ██████████               █████████     → 少し楽になる程度
 実装       ████████████████████     ████          → ★ 大きく縮む
 単体テスト ████████████             ████          → ★ 大きく縮む
 結合・受入 ████████████             ███████████   → ほぼ変わらない
 障害対応   ████████                 ███████       → ほぼ変わらない
```

**なぜ全体は縮まないのか**
- 縮むのは「**手を動かす時間**」だけ
- 縮まないのは「**決める・合意する・確かめる時間**」
- 全体の効率は、**縮まない部分の比率**で頭打ちになる

### 話すこと
- 実装が劇的に速くなるのは、今日体験したとおり本当です。ただ、そこだけを見て全体工数を割り引くと、必ず破綻します
- お客様との仕様調整も、結合テストの環境待ちも、障害の原因調査も、AIでは短縮しにくい
- 「実装が全工数の3割で、それが1/3になった」なら、全体は2割減。**桁で変わる話ではない**、という感覚をまず持ってください

## スライド2

### メインメッセージ
> **ボトルネックは「上流」と「検証」に移動する**

### 見せるもの

**📉 減る仕事 / 📈 増える仕事**

| 📉 減る | 📈 増える・新しく発生する |
|---|---|
| 定型的な実装 | **仕様の明文化**（AIが読める粒度まで書く） |
| テストコードの記述 | **生成物のレビュー**（量が増える） |
| 単純な変換・移植作業 | **テスト観点の設計** |
| 「調べながら書く」時間 | **ルール／プロンプト整備**（初期投資） |

**⚠ 見積りでやりがちな事故**
```
 ❌ 「実装が速いから」と全体を一律で割り引く
      → 縮まない工程まで削られ、後半で破綻

 ❌ レビュー工数を据え置き、または削る
      → 生成量は増えているのに見る人が足りず、品質事故

 ❌ ルール・設計書の整備コストを見ない
      → 立ち上がりで想定より工数を食い、効果が出る前に息切れ
```

### Take away
- 🎯 **一律の掛け目で見積もらない**。工程ごとに効き方を分けて考える
- 🎯 **初期投資を必ず積む**。ルールファイル・設計書の整備は、後から効いてくる先行コスト
- 🎯 **レビュー工数はむしろ増やす**。作る量が増えれば、見る量も増える
- 🎯 効果が出やすいのは「**同じものを大量に作る**」PJ。1本ものの難所解決には効きにくい

### 話すこと
- このあとのシミュレーションで、自分のPJへの適用を考えていただきます。その時に「AIでどれくらい速くなるか」を一律で置かないでください
- 見るべきは、**自分のPJの工数のうち、実装とテストコード記述が何割か**。そこが小さいPJでは、効果も小さい
- 逆に、画面や帳票が大量にあるようなPJは相性が良い。その見極めをするのが今日の最後の課題です
