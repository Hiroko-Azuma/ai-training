# 小話06　同じ指示なのに、毎回結果が違う

|項目|内容|
|---|---|
|分類|🔧 仕組み|
|尺|4分（スライド2枚）|
|推奨タイミング|機能追加の待ち時間／隣同士で結果が違うと気づき始めた頃|

---

## スライド1

### メインメッセージ
> **AIは「同じ答えを返す装置」として作られていない**

### 見せるもの

**掴み：隣の人と同じプロンプトを打ったのに、出てきたコードが違う**

**理由：次の1語を"選ぶ"ところに、ゆらぎがある**
```
 「public class Book」の次に来る語の確率
        ┌──────────────────┐
        │ Controller  41%  │ ─┐
        │ Service     27%  │  │ ← 毎回この分布から
        │ Entity      18%  │  │   "サンプリング"して選ぶ
        │ Repository  09%  │ ─┘
        └──────────────────┘
                ↓
        1語ズレると、その後の全部がズレていく
```
- 常に最上位を選ぶ設定にすれば揺れは減るが、**ゼロにはならない**
- 実行環境・並列処理の都合でも、わずかな差が出る

**ゆらぐもの / ゆらがないもの**

| ゆらぐ | ゆらぎにくい |
|---|---|
| 変数名・メソッド名の付け方 | 設計書に明記された項目名 |
| コメントの文言 | ルールファイルで縛った書き方 |
| 実装アプローチの選択 | 完了条件（テストが通る／通らない） |
| 説明の言い回し | 既存コードに倣った構造 |

### 話すこと
- 「同じ入力 → 同じ出力」は、我々が慣れているプログラムの性質です。AIはそうなっていません
- 次の1語を確率分布から選んでいるので、**1語違えば、その後の展開が全部変わります**（→ 小話05と同じ仕組みの、別の顔）
- ここで大事なのは「困ったね」で終わらないことです。**ゆらぐ部分と、ゆらがせない部分を分けて設計する**のが実務です

---

## スライド2

### メインメッセージ
> **品質は、プロンプトの言い回しではなく「ルールと検証」で担保する**

### 見せるもの

**❌ 再現性を、プロンプトで作ろうとする**
```
 「さっきと同じように書いて」
 「前と同じ感じで」
      └ 前がどうだったかは、AIの側に残っていない（→ 小話01）
```

**✅ ゆらいでも同じ結論に落ちる仕組みを置く**
```
 ┌─ 縛る ─────────────────────────────────┐
 │ CD_ルール.md     … 書き方を固定           │
 │ モジュール一覧.md … 名前を固定             │
 │ 外部設計書        … 仕様を固定            │
 └────────────────────────────────────────┘
                 ↓  それでも残るゆらぎは
 ┌─ 検証する ──────────────────────────────┐
 │ mvn compile     … 存在しない書き方を落とす │
 │ 単体テスト        … 振る舞いを固定         │
 │ 人のレビュー      … 仕様との一致を見る      │
 └────────────────────────────────────────┘
```

**運用の考え方が変わる**

| 従来の感覚 | AI時代の感覚 |
|---|---|
| 手順どおりなら同じ物ができる | **毎回違う物ができる前提で設計する** |
| レビューは抜き取りでよい | **出力は毎回見る**（同じ結果の保証がない） |
| 良い出力が出たら手順を記録 | 良い出力が出たら**ルールファイルに書く**（→ 小話14） |

### Take away
- ✅ **再現しないのは不具合ではなく仕様**。「同じにならない」を前提に運用を組む
- ✅ ブレを消したい所は、**プロンプトでお願いするのではなくルールと設計書で縛る**
- ✅ 最後の砦は**機械的な検証**（コンパイル・テスト）。ゆらいでも、ここは通るか通らないかで決まる
- 💡 うまくいった時こそ**ルールファイルに残す**。次も同じ結果を引くための唯一の方法

### 話すこと
- 「隣の人と結果が違う」は、今日この後もきっと起きます。その時に「自分のやり方が悪いのか」と悩まないでください。**そういうものです**
- 実務で怖いのは、レビューで一度OKを出したパターンが、次回は違う形で出てくること。だから**言い方で揃えようとせず、ルールとテストで揃える**
- これは我々の得意分野です。**再現しないものを、検証で押さえ込む**。テスト設計そのものですよね

## 補足（質問が出たら）
- **Q. temperature を0にすれば同じ？** → 揺れは大きく減るが、環境要因もあり完全な再現は保証されない。「ほぼ同じ」まで
- **Q. 同じ結果が欲しい場面は？** → その処理はAIではなくコードで書くべき、というサインでもある
