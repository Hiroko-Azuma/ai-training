SLIDE 1 変更範囲は頭の外に出る
AIは、あなたが思っているより
広い範囲を書き換える

掴み ──「関連する箇所も直しておきました」

依頼： 「BookDeleteController に削除確認を追加して」
MBookDeleteController.java← 頼んだもの
MBookService.java← 頼んでいない

Mテンプレート 3枚← 頼んでいない
M既存のテスト 2本← 頼んでいない ★危険
計 8ファイル変更

…この状態から「さっきの状態に戻して」と言えますか？

AIの特性として、こうなる

特性結果
一貫性を保とうとする呼び出し元・関連クラスまで直しにいく
止まらずに進む気づいた時には広範囲が変わっている
悪気なく"良かれと思って"やる既存の動いていたコードまで書き換わる
途中で止まることもある中途半端に変更された状態が残る
⚠ 一番怖いのは「壊した」ではなく「どこが変わったか分からなくなる」こと
🎤 話すこと（登壇メモ）
  • 手で書いていた頃は、変更範囲は自分の頭の中にありました。AIに任せると、変更範囲が自分の頭の外に出ます
  • しかもAIは親切なので、頼んでいない所まで整合性を取ろうとして直します。多くは正しいのですが、既存のテストを直されるのは相当危険です
  • ここで唯一の安全装置がGitです。Gitは今までも大事でしたが、AI時代は位置づけが変わります
SLIDE 2 守るのは2つのタイミングだけ
「いつでも捨てられる状態」を保つのが、
速さの前提条件

🔒 2つのタイミングだけ守る

TIMING 1
① AIに投げる前 → コミット
きれいな出発点を作る。ここに戻れる
TIMING 2
② 動いたら即 → コミット
戻れる着地点を確保する

AI時代のコミット粒度

従来AI活用時
機能が完成したら1回の指示ごとでよい
きれいな単位で汚くてよい。後でまとめられる
メッセージを丁寧にWIP: BK01削除 AI生成 で十分
変更を積み上げる捨てる前提で積む

差分レビューが、そのまま作業になる

git diff ／ VS Code のソース管理ビューを開いて、上から順に。

頼んでいないファイルが変わっていないか最初に見る
既存のテストが書き換えられていないか特に重要
中身が仕様どおりか→ 小話15
🚗 Gitはシートベルト 事故らない自信ではなく、事故った時に助かるために締める

🎁 Take away

  • ✅AIに投げる前にコミット。これだけで、やり直しのコストがほぼゼロになる→ 小話11
  • ✅粒度は細かくてよい。きれいさより、戻れることが優先
  • ✅レビューの入口は「変更ファイル一覧」。頼んでいない所が変わっていたら要注意
  • 🚗Gitはシートベルト。事故った時に助かるために締める
🎤 話すこと（登壇メモ）
  • 言っていること自体は当たり前です。ただ、AI活用ではこの当たり前の効き目が桁違いに大きい
  • 戻れる状態があると、思い切って任せられるようになります。逆に戻れないと、慎重になりすぎてAIの速さを活かせません
  • 今日のハンズオンでも、CD実行の前・UT実行の前に一度コミットしてから進めてみてください。安心して捨てられるというのが、どれだけ作業を速くするか体感できると思います
